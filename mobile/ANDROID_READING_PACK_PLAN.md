# Android reading packs · technical plan and launch packet

November 11, 2026 · `mobile/store-mvp` · Draft PR #1

## Bounded product scope

Free install with offline Daily Signal, Echo Journal and Revisit the Pattern. A limited introductory AI allowance and one repeatable finite pack cover the existing seven-layer lens. Two introductory readings and one 20-reading pack at $1.99 are sizing assumptions for the pilot. The owner must approve the commercial terms. Defer subscriptions, Follow the Thread, AI revisits, cross-store balances and multiple pack sizes. The branch still uses the original store-license access flow. Intro credits, pack checkout, and restoration described here are planned work.

## Billing, credits and recovery

1. **Buyer identity and trial.** Daily Signal and the journal require no sign-in. Before granting introductory AI credits or starting checkout, authenticate a stable buyer account that can be recovered after reinstall. Grant intro credits once per verified buyer through a unique ledger event. Use install and IP limits plus a server-verified Play Integrity verdict bound to trial and purchase requests. Treat device and account signals as abuse controls with a retry/support path. Use an opaque buyer reference for Play's obfuscated account ID. Keep Play verification and journal storage separate. Design in-app and web account deletion before offering account creation.
2. **One Play product.** Use Google Play Billing for the consumable digital pack in the standard Play distribution. Use a currently supported library, with v9 as the integration target. Query product details and price from Play. Send the token to the server with an authenticated session. Verify the expected package, SKU, quantity, buyer binding and PURCHASED state using the Google Play Developer API. Pending, canceled, unknown and mismatched purchases grant zero credits. Keep Publisher credentials server-side.
3. **Idempotent grant and consume.** Store a unique purchase-token record, buyer, SKU and credit grant in one transaction. Keep the original token securely for Google requests and avoid logging it. After committing the grant, consume on the server through a durable retry queue so the pack can be purchased again. Reprocessing a token returns its existing result. Handle the three-day acknowledgement window, including a crash between grant and consume. Reconcile already-consumed tokens without issuing a second grant.
4. **Spend and restore.** Maintain intro and paid credit events separately. Reserve a credit transactionally with a stable request ID before starting a reading, finalize it on delivery, and release it if the reading fails. Retries must reuse the same operation and recover the prior state. Provider spend reservations remain separate, since a failed reading can incur generation cost. On reinstall, restore unspent credits from the authenticated buyer ledger. Query unconsumed Play purchases on reconnect. Consumed packs need the server ledger for restoration.
5. **Refund and fraud reconciliation.** Treat Play notifications as a signal to reverify state. Reconcile against the Voided Purchases API as a backstop. Track credits by pack so a refund removes remaining credits from the affected grant once. For consumed value, record the deficit for abuse review and prevent further use of reversed credits. Protect notification ingress, persist replay keys, retry transient failures, and alert on consume/reconciliation backlog. Report purchase and reading health using aggregate events without journal content.
6. **Release gate.** Verify purchase success, pending to paid, cancel, duplicate notifications, replay across accounts, consume timeout, concurrent credit spend, reinstall, refund after use, account deletion and budget exhaustion. Use Play license testers before taking real payments. Existing app-license verification is useful for distribution proof, but it cannot verify or restore pack purchases.

## Spending ceiling and operations

- `MOBILE_MONTHLY_API_BUDGET_USD` defaults to `5`. `0` closes the completion gate. Set `MOBILE_SPEND_DB` to an absolute SQLite path on the verified persistent mount. Initialize an empty file once on that mount, for example with `touch /var/data/eidomancer-spend.sqlite`. The service refuses a missing file. Preserve the file across restarts and updates. Share it across every server process spending on the same key; keep the pilot on a single host with a local disk. An old backup can undercount recent reservations, so reconcile against provider usage before re-enabling after recovery.
- The guard reserves the published 400,000-token input context ceiling plus the 1,050-token completion limit at standard uncached rates, up to **$0.304725** per pending reading. SQLite serializes reservations. Valid usage settles to the uncached-rate calculation, even when downstream parsing or moderation rejects the reading. Missing usage, timeout or process interruption retains the full hold. Unexpected model, tier or usage beyond the metered bounds halts future generation, including across UTC month changes, until investigated and reconciled. When available headroom is smaller than a hold, readings pause even if the settled ledger is under $5.
- The ceiling covers this service's completion requests using the pinned model and standard public OpenAI endpoint, measured in each request's start month in UTC. This is an application accounting ceiling based on the stated rates and model contract. Keep the evaluation CLI and other consumers on separate restricted projects or keys with separate budgets. Use provider-side enforced limits if available as a second layer and monitor for delays or rate changes. Moderation uses OpenAI's free endpoint.
- Keep the earlier proposed $45 first-month authorization envelope before tax, with $25 Play registration if required, up to $15 isolated hosting with persistent storage, and $5 for API generation. Set the pilot daily ceiling to 20 attempts. At the example stress cost it models $3.95 across 31 days, with the SQLite ceiling as the binding backstop. No hosting or store spend was approved by this plan.

## Listing concept and disclosure draft

**Name** · Eidomancer: Daily Reflection

**Short description** · A daily symbolic lens for decisions, patterns, and what happens next.

**Description draft** · Start with a Daily Signal. Bring a decision or recurring experience to Eidomancer for a seven-layer reflection. See what the reading drew from your account, where it is uncertain, and what might change it. Save the readings you choose to Echo Journal and return with what happened next. Daily Signal and saved entries work offline. AI readings require a connection and include a limited introduction. Optional packs add a stated number of readings.

Show four screenshots in this order: Daily Signal, a first reading card, the evidence layers, and Revisit the Pattern. The demo shows save and compare with a clearly fictional account. Final store copy must use the approved allowance and match the real app. Keep pack purchase details visible before checkout.

**Privacy draft for the proposed release** · Daily Signal runs locally. Saving or revisiting a journal entry sends nothing from that entry. Explicit AI submission sends the typed account to the service and OpenAI to moderate and generate a reading. An explicit report sends the reported reading and selected reason to the service for review. The local journal is separately deletable from the buyer account. Device or backup access may expose the journal. Purchase and recovery features use a buyer identifier, installation/security signals, verified transaction records and credit history. Google Play handles payment details. Before submission, fill in verified retention periods, recipients, support contact, account and data deletion paths, and required financial record retention. The current in-app privacy copy describes the existing release, before buyer accounts and packs.

## Tester onboarding draft

Install from the Play test link after opting in with the same Google account you use in Play. If the closed-test rule applies, stay opted in for the full period. Use a synthetic example for your first AI reading. Open all seven layers, save the reading, switch offline, add an observation in Revisit the Pattern, then reopen and delete it. For license-test purchases, use the designated test account and a Play test payment method. Stop at checkout if it shows a real payment method. Try reinstalling and signing back into the buyer account to check credits; local journal entries have device-local retention. Use the in-app report action for an unsuitable reading. For feedback, send the build number, device, time, steps, expected behavior and actual result. Omit personal journal text, credentials and purchase tokens.

## First genuine paying customer

Confirm the account and price, finish and validate the one-pack ledger and recovery flow, approve a small isolated pilot and live model validation, complete Play testing and approvals, and release to one initial market. Use an owned channel and a direct store link to find qualified readers. Track aggregate listing visits, installs, completed intro readings, revisits and paid purchases. Count the first customer when a genuine Play payment is verified and credits are delivered, with refund reconciliation. Tester purchases and parser acceptance are separate from paid conversion.
